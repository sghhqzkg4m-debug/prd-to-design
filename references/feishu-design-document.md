# 飞书设计文档收敛规则

飞书设计文档面向设计评审，不是产品、架构、接口和前端实现规格的合集。目标是让评审者快速判断：为什么做、为谁做、任务如何完成、页面怎样组织、状态与风险如何反馈、设计是否可验收。

## 体验目标、设计目标与讲解顺序

- 推荐讲解顺序为“业务背景、业务目标与版本定位 → 用户、JOB、Case 与目标体验／设计目标 → 竞品参考与设计取舍（有研究价值时）→ 本期方案与页面交互 → 待决策 → 验证”。固定叙事原则，不固定章节数量、编号或名称；简单任务允许合并。各维度是否显示按 [feishu-analysis-framework.md](feishu-analysis-framework.md) 判断。
- 开篇只用短段落说明业务背景、业务目标与规划确定的版本定位，并标注来源。规划缺失或冲突时写明待确认，不由设计分析代替规划定性；有主次目标时沿用规划结论。需求材料明确指出承接的战略或 OKR 时，在可选的“业务驱动与价值”中简述其方向、本需求的承接关系和来源；不能仅凭行业趋势或功能内容反推战略、KR 或收益数字。Case 中将用户完成任务时应获得的体验改善融入关联的体验目标，使业务结果与用户体验相互支撑，不再并列设置重复的目标卡片。不默认输出目标大表、范围表、完成标准或待确认清单，也不在摘要和首章重复同一组结论。
- 完成标识放入对应 Case 与验收；凭证安全、权限和高影响操作要求放入对应页面。收益基线与测量限制放入验证说明，不在开篇堆叠防御性声明。
- 待决策集中放在方案之后，读者理解方案后再讨论问题。影响当前页面解读的假设必须在对应任务、页面或规则处就地简短标注，可引用待决策编号；不得为流畅叙事把未确认规则写成事实，也不在开篇铺开编号。
- 按“体验目标（业务进步与体验变化）→ 设计重点 → 设计目标”推导。先校准 JOB：任务是否能支持用户在具体情境中取得进步、范围是否适合本期；再识别用户为取得进步所追求的体验，只选与业务结果直接相关的诉求。将业务进步与体验变化合写为一条体验目标，保留“使哪个角色从有证据的现状负担转向什么目标体验”；没有现状证据时只写期望改善，不虚构前后变化。目标不用两个标签或两段话并列呈现，也不含设计手段。设计目标由综合目标推导，写清任务关键环节、角色、针对设计重点的设计策略和预期体验品质；策略要说明如何帮助角色判断、行动或理解结果，不能只写“预检查”“反馈机制”等孤立名词，也不写固定控件或未经确认的能力。检查体验品质是否可衡量、是否形成有价值的差异、是否符合产品价值主张并照顾用户情感因素；没有证据不编造优势或数值。目标中点明关键策略，具体页面和交互规则留在方案，完成标识留在 Case，观察标准和验证方法放在验收；业务指标不直接充当设计目标。
- 每个 Case 单独写设计目标。通用组织方式是“在[场景]，通过[关键设计策略]，让[角色]获得[体验改善]”。可按任务特点调整语序与重心：**前后变化式**表达有证据的现状阻碍如何借助策略转向目标体验，仅在现状有证据时使用；**关键决策式**表达策略如何帮助角色理解关键判断及后果；**协作交接式**表达策略如何让相关角色以更清楚的边界或更轻的负担完成交接。三种写法是选择依据而非必填模板，不与场景类型机械绑定；目标句只保留能说明“怎么改善”的关键策略与体验改善，具体操作和“能否”检查移到方案与验收。
- 每个 Case 的设计目标都要同时回应综合目标中的业务结果与体验诉求；两者无法形成有意义的关系时，检查目标、Case 范围或证据，不硬凑手段。HTML 中按“体验目标 → 设计重点 → 设计目标”纵向呈现，飞书文档也保持同样的推导关系。Case 完成标识留在任务说明，验证方法留在验收章节，不为目标额外生成独立的“观察标准”卡片。创建对象、拿到配置、真实接入成功和持续可用是不同阶段，不能互相替代；原型模拟也不能证明真实业务完成。
- 设计目标下的“衡量标准”仅在指标口径、测量方式和目标值都有可靠依据时显示，并写明统计周期；缺少任一项就省略整行，不显示“XX”“待定”等占位。暂不可量化时，把可观察的行为与结果标准放在验收章节，不用主观数字替代证据。
- 写完目标后做一次反向检验：体验目标若只是在列举“建设入口、支持策略、提供密钥”等能力，应改写为目标对象实际发生的业务变化；若只写“简单、清晰、能完成”，应补足业务结果与 Case 中希望改善的体验品质，但不塞入方案。设计目标若只重复综合目标而没有明确的设计策略，就不能指导取舍；策略若只是抽象名词，需说明其如何作用于当前任务；若变成按钮、字段或步骤清单，应上提到策略层并把细节移到方案；“能判断 A、能解释 B、能修正 C”这类任务检查清单移到验收。关联使用语义名称或 Case 上下文，不为目标自造字母编号；无法连通时标记证据缺口，不伪造用户问题或收益。
- 角色覆盖关键交接双方；岗位归属不明时标待确认，不预设客户组织。平台能力应映射到结果导向的 Job，而非直接用算法名作 Job。
- 不编造效率、成本、成功率收益或客户情绪。定量目标需要基线与证据，缺少时用任务观察验证。
- 明确区分用户要求、设计建议和待确认约束，尤其是最小数量、禁用组合、权限和上线范围。

## JOB、Case 与场景阶段

- JOB 描述用户为达成业务结果所需的一组任务，采用“xxx（用户）需要在 xxx（场景）下，完成／进行 xxx（任务）”。避免用菜单、按钮或单一步骤替代 JOB。
- Case 描述 JOB 下由具体情境触发的任务场景，采用“在 xxx（场景）下，完成／进行 xxx（任务）”。为每个 Case 补充起点／前提和可观察的完成标识。
- 阶段是完成 Case 的步骤。不得把同一场景中的准备、配置、交接等连续步骤机械拆成多个 Case 或 JOB。不同触发条件、协作路径或完成结果才构成拆分依据；不固定 JOB、Case 或阶段数量。
- 异常作为对应 Case 的分支合并呈现，写清触发条件、用户可见反馈、可执行操作、恢复或退出路径及恢复后的完成标识，不另建异常 Case。首次路径只在相应 Case 中保留失败时的交接与返回，避免暗示所有成功任务都必经排障。
- “简单、安全、高性价比”等上层诉求可保留为背景，并映射到本功能的业务任务；不擅自把诉求全部纳入本期。

## 用户旅程的选择与展示

用户旅程的分析、证据和表达规则由 `user-journey` 维护。任务跨阶段、角色或触点且有交接与体验断点，或用户明确要求旅程时，读取并调用该 Skill；单页短任务保留任务流程。传入已有 JOB、Case、角色、目标、来源和范围，返回结果完整嵌入本需求文档的原旅程位置。集成约定见 [html-current-journey.md](html-current-journey.md)。主文档继续负责目标校准、章节去重及页面与验收追踪。

## 章节合并与追踪

- JOB、Case、角色定义与对应旅程集中呈现，或拆成相邻的“JOB 与角色”和“Case 旅程”章节。已有角色表、核心任务表、任务闭环图中重复的动作与交接合入旅程，不重复保留一整套叙述。
- 本期范围放在整体方案开头，默认用“用户任务 / 本期设计覆盖”简表，非范围以短说明补充；少量内容可直接用段落。不默认增加“待确认边界”列，完整问题清单归入待决策。旅程不再承载完整范围清单。
- 保留“体验目标→ 设计目标 → Case／阶段 → 设计策略 → 页面／验收”的必要追踪，并检查设计目标同时回应其中的业务结果和体验改善；短引用即可，不另建重复的大表。客户特征、落地障碍、版本分期与收益按触发条件融入现有章节，不另建固定的并列章节。
- 更新时先确认替代内容完整且可读，再移除被替代的章节／图表；核对编号、交叉引用、人工补充和原生组件是否保留。

## 内容重心参考

触发竞品研究时，调用 `competitive-analysis` 的产品功能体验研究模式。正文按设计问题呈现关键比较与取舍；独立竞品文档承载完整证据、评分依据与缺口。未触发时不为形式完整强制增加竞品内容，也不把竞品先例当成本产品体验已验证。

- 约 70%：用户任务、现状与目标体验、信息架构、流程、页面和交互。
- 约 20%：状态、权限、安全、异常反馈和恢复。
- 约 10%：直接影响交互的技术约束、证据缺口与待确认项。

比例用于控制重心，不要求机械统计字数。

## 主体应关注

1. 设计结论：问题、推荐方案、核心体验、范围。
2. 用户与场景：角色、触发条件、Job、完成标识。
3. AS-IS / TO-BE：体验断点与目标路径。
4. 范围与关键约束：本期、非范围、会改变页面的依赖。
5. 信息架构与入口：候选比较、选择和取舍。
6. 核心任务流程：主路径、分支、失败和恢复。
7. 页面与交互：信息优先级、结构、操作、反馈、线框。
8. 状态、权限与异常：可见性、可操作性、危险操作与恢复。
9. 关键文案：状态、校验、成功、失败和确认。
10. 设计验收与待确认：任务完成性、高风险状态和真正会改变设计的问题。

章节可根据复杂度合并，不要求固定数量。

## 下沉或压缩

以下内容仅在直接改变入口、字段、状态、权限、反馈或恢复时，以一两条约束或待确认项保留；否则移入技术规格或附录：

- 后端组件选型、部署位置、网络拓扑和配置权威。
- 路由、Hash、轮询、冷却、探测和限流的底层算法。
- 完整协议矩阵、接口字段、错误码和重试实现。
- P95/P99、吞吐、容量和分布式实现。
- 用户不可见、不可操作的完整技术对象模型。
- 全量需求追踪、接口追踪和测试数据。
- Workspace 路径、工具日志、授权过程和生成步骤。

## 仍需保留的技术约束

技术问题会直接改变用户体验时不能删除。例如：

- 流式响应开始后能否切换实例。
- 成员异常时聚合状态如何变化。
- 删除或停用影响哪些用户对象。
- 密钥是否只展示一次。
- 两类接入来源是否允许混选。
- 模型不一致时能否提交。
- 配置是立即生效还是需要发布。
- 并发编辑冲突如何处理。

文档描述用户可感知语义和设计处理，不代替研发给出底层实现。

飞书设计文档回答用户为什么来、怎样完成任务，页面展示什么、如何决策与恢复，以及设计选择和可验收结果。实现级组件、接口、文件计划和 Mock 留给单独的技术规格，不作为本 Skill 的默认交付。
