# 需求与交互分析方法

本文件把需求拆解、Job、能力边界和高风险分析内置到主 Skill。它只规定分析方法；最终交付物、章节、HTML 模板、飞书组件和 Markdown 是否对外输出，均以主 Skill 和 [deliverable-schema.md](deliverable-schema.md) 为准。不要套用另一套默认 Markdown＋HTML 交付规则。

## 从证据到验收

以“证据 → 问题 → 业务结果与目标体验 → Job／Case → 能力与规则 → 页面行为 → 验收”建立追踪。先分清用户问题、业务诉求、技术约束和材料中预设的解决方案；每项关键结论注明来源及已明确、推断或待确认。截图和竞品做法只构成参考证据，不自动变成本产品需求。来源冲突时保留冲突，用户最新确认覆盖旧假设并同步修正受影响的流程、状态、页面和验收。

只有一句模糊想法，且产品、角色或目标不足以形成可靠分析时，先给出简短的结论、已知证据、可能的 Job 和最关键的补充问题，不为凑齐 HTML 编造入口或规则；信息足以判断任务与设计方向后，按主 Skill 的交付模式生成或更新产物。

## 产品上下文与入口判断

核查产品定位、角色、现有导航与任务路径、核心对象、权限／状态模型、截图／设计稿／代码和交互惯例。已有产品新增功能优先还原当前触发点、对象、入口、路径与复用模式，再判断新能力如何接入。

| 证据程度 | 允许的判断 |
|---|---|
| 充分 | 给出有依据的现状路径、推荐入口、页面归属和目标变化 |
| 部分充分 | 比较 2–3 个入口或载体候选，写明成立条件、代价、风险与验证方式 |
| 缺失 | 只确定产品无关的 Job、对象、能力和风险；入口与页面归属保持待核查 |

不能用行业常见模式冒充当前产品事实。无法访问产品页面时使用用户已提供的材料继续分析并说明证据缺口。若用户要求确定入口或页面载体，而产品上下文不足，就明确指出需要补充的证据。

## 多需求归并与 Job

输入含多个需求时，先为原始条目建立可追踪 ID，记录来源、角色、触发条件、对象、期望结果、风险和确定性。拆开混合了不同角色、对象或结果的条目；合并结果与规则相同的重复项；标出目标、权限、范围或规则冲突；识别前置依赖和共享能力。清单用于分析，主交付呈现归并后的结论；完整逐条追踪仅在有助于评审或用户要求时展开。

Job 表达用户在具体情境中希望取得的进展及其更高层结果，不用页面、按钮或单个操作命名。检查其角色、触发条件、核心对象、现状做法及痛点、完成标识、关联需求和证据状态；粒度应有可识别的起点与结果。主 Skill 的“JOB → Case → 场景阶段”用于最终叙事：Case 承载具体场景、体验目标、设计重点、设计目标、路径与异常，不把能力模块误当 Case，也不把页面误当 Job。

## 能力边界与共享规则

用“业务域 → Job → 能力模块 → 交互与规则”整理复杂输入。能力模块围绕稳定的用户结果与任务闭环；同一 Job、核心对象、连续路径、角色权限和生命周期相近时合并。角色或结果、对象、生命周期或权限明显不同，或能力可独立验收、被多个 Job 复用时，考虑拆分或抽出共享能力。搜索、通知、审批、审计、导入导出等先判断是模块专属还是共享；页面、弹窗、表单和控件不自动成为模块。

模块只是内部分析和必要的方案结构，不按需求条数或模块数量增加交付文件。低风险内容压缩表达；高风险内容在同一主交付的相应 Case、页面、状态或附录中展开。同一规则只保留一个权威位置，其他位置用简短引用关联。用需求 ID → Job／Case → 能力／规则 → 页面或流程 → 验收的链条检查遗漏，不为追踪另造重复正文。

## 高风险交互展开

当存在复杂状态、权限、不可逆操作、异步任务、部分失败、并发冲突或跨角色交接时，围绕相关 Case 和能力核查：

- **现状与方案**：有证据才确定 AS-IS；TO-BE 写明哪些节点新增、删除或改变，区分事实、还原、推断与方案。
- **对象与入口**：对象含义、关系、所有者和生命周期；页面职责、信息优先级、进入与退出、复用或新增依据。
- **主流程与分支**：触发条件、每个角色的判断和操作、系统反馈、结果承接、取消／回退，以及异常返回到哪一步。
- **状态与权限**：事件和前置条件、可见与可操作范围、数据范围、禁用原因；加载、空态、成功、失败和权限不足的反馈。
- **风险与恢复**：影响范围、确认和撤销；输入保留、重复提交、对象失效、并发修改、异步进度、部分失败后的重试或退出。
- **验收**：对正常、异常和权限条件分别写明前提、动作、界面反馈、结果与恢复；业务指标仅在口径、基线和测量方式可靠时量化。

仅展开会影响设计取舍和验收的部分；后端选型、接口细节与完整技术对象模型仅在直接影响交互时进入设计正文，其余交给技术规格。缺乏证据的规则写成待确认，不补造默认值、权限或 API。

## 可视化与追踪

先说明图帮助判断什么。关系用关系图，顺序和分支用流程／泳道图，层级用结构图，生命周期用状态图，条件组合用决策表，权限或方案差异用矩阵，已确认页面布局用线框。图的内容标明现状事实、现状还原、推断或设计方案，并靠近证据与结论；一段文字更清楚时不强制画图。图形数量随任务复杂度决定，不为充实报告重复表达。
