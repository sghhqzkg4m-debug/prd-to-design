# HTML 模板复用与结构校验

## 固定结构与可变内容

从实际采用的模板原文件复制产物。固定六章标题、顺序、目录锚点、主要组件所在章节、CSS 和交互脚本；在原组件内部替换文本、追加 Case 和行。不要通过重写整章 HTML 或另造同名组件来填充业务内容。条件内容可按证据省略，但不能把已使用的旅程、流程、线框降级为普通表格或文字摘要。

首页标题在桌面宽度尽量保持一行，窄屏可自然换行。副标题要用本项目的一句总结，不能保留固定流程文案；不再另写与第 01 章重复的第三行说明；不显示右下角装饰底图和侧栏模板说明。现状、目标旅程标题须有清晰类别与分隔，阶段和步骤数量由任务决定。竞品议题来源和本轮判断合并为一个默认折叠区。主模板只含六章，不恢复独立状态、验收或使用说明章。关键文案写入流程节点与页面反馈，不设独立表。状态、权限和异常恢复写在触发流程节点，仅跨步骤共性约束集中说明。线框按已核查的平台框架绘制完整画布，平台未核查时只展示结构示意。

模板中的“必需／条件必需／可选／有可靠数据时可选”等角标只指导编写，生成成品 HTML 时删除角标元素，保留适用的章节标题与内容。模板章节导语若是“交代……”“先给出……”等写作指令，替换为本需求的实际内容概述。正文直接陈述业务事实和设计结论；不要在 Job、目标、业务背景等叙事段落插入“原材料的……是上位价值”“客户材料明确”等编写过程说明。必要的来源与证据边界放在对应结论的简短来源标记或附录，不复制来源文本的分析过程。模板中的填写规则、交付检查、组件选择说明也不进入面向产品评审的正文。

竞品章节采用固定的“议题来源与本轮判断（一个默认折叠区）→ 三列对照表 → 我方取舍与详报链接”结构。三列表头为“设计议题”“具体竞品、参考功能与功能亮点”“可参考的点”；行由本需求的设计议题驱动。第二列按竞品分段写“具体竞品”“参考功能”“功能亮点”，把产品来源、可核查的具体功能、对用户任务的作用分开，必要时一行列多个竞品；资料限制使用低强调文字，不使用彩色“边界”标签，完整缺口由详报承载。第三列写本方案的适用条件、取舍与验证。“议题来源”明确写出体验目标、设计目标与设计议题的对应关系，以现状断点校准优先级，议题标题用陈述句。证据不足时明确说明，不编造完整体验评分，也不退化成按来源列事实的表格。正文所有真实链接，包括表格单元格、已访问链接与详报入口，使用蓝色加下划线及清晰悬停态；不得继承灰色正文色。

主文竞品表每一行与独立竞品报告的概览卡、逐题研究单元一一对应，三个位置沿用同一陈述式议题标题和唯一研究锚点。细分或合并研究问题时同时更新两份文档及目录链接；校验不仅检查链接存在，还检查数量、标题和锚点一致。

同一组件在所有 Case 中使用同一结构。阶段数、角色数、动作列数和连线随任务变化；不能为统一外观强行使用相同业务步骤，也不能因为某个 Case 内容较少就另造简版组件。没有证据的体验行可以删除，同时移除对应筛选项。

需要改变组件能力或结构时，先修正模板与共享脚本，再同步项目产物。业务数据放在内容或组件数据属性中，不修改项目 HTML 的共享 CSS/JS 来硬编码某一个 Case。

## 多 Case 旅程

使用 `scripts/render-journeys.py` 将所有 Case 的数据一次生成到同一份 HTML 片段，再填入主模板的旅程位置：

```sh
python3 scripts/render-journeys.py journeys.json journeys-fragment.html
```

输入结构见脚本顶部说明。每个 Case 都有相同的上下文四栏、图例、全屏/筛选工具栏、两级表头、角色泳道、动作节点、交接及异常连线、逐动作体验与证据行、交接说明。输入内容是文本，不接收任意 HTML。`id` 必须唯一；动作列由 `actions` 决定，阶段跨度总和必须等于动作数量；连线端点只能引用当前 Case 动作。

模板的运行脚本遍历所有 `.journey-flow[data-journey-links]`，逐图绘线。不得恢复为只查找一个固定 `journey-flow` ID 的脚本。所有节点 ID、SVG 箭头标识、筛选目标都按 Case 隔离。

页面流程节点写明“平台名称－具体页面”；真实平台与页面名需核查，跨平台交接同时注明来源和目标。主路径和失败返回使用图例、不同线型及必要的留白标签。页面流程连线须按节点所在网格行判断是否同排，不能用不同高度卡片的中心点误判；同排行只走水平直线。跨行预留足够行距，标签放在连线上方且不遮挡节点或线；容器不足时优先加宽可横向滚动的流程画布。流程节点卡片按内容自适应宽度，在可读的最小与最大宽度之间变化；不得为对齐把同排短内容卡片拉成与长内容卡片等宽。页面流程的主线按节点空间关系连接：同一行走水平线，同一列跨角色走垂直线，斜向交接仅在节点之间的留白处转折；不要从节点右侧绕回同列下方或让线穿过节点。失败返回从触发节点下缘进入底部预留回路，再指向目标节点下缘；同一步骤内修正只用节点内文案，不画自环。修改连线能力时同步模板脚本与已生成 HTML，并检查不同角色、列数和节点高度的 Case。

## 交付校验

```sh
node scripts/validate-artifacts.mjs <output-dir> --competitive
python3 scripts/validate-template.py <document.html> [template.html]
```

主校验脚本会对文件名包含“交互设计需求分析”或“design-analysis”的 HTML 自动执行模板检查。其他命名需显式运行 `validate-template.py`。使用用户指定模板时给主校验脚本传入 `--template=/absolute/path/template.html`，不得用参数跳过已知结构错误。

模板检查覆盖六章、标题、目录、主要组件归属、共享 CSS/JS、重复 ID，以及每张旅程的组件层级、动作列对齐、阶段跨度、筛选与全屏、连线端点。单纯检查文件存在或语法正确不能作为“严格按模板”的证据。校验失败先修复；静态结构校验仍不能替代桌面与窄屏视觉检查、筛选和全屏实际操作。浏览器能力受限时如实记录未完成的检查，不声称已验证渲染。

旅程连线标签须按实际文字宽度测量，并避开动作卡片和其他标签；同排标签优先放卡片上方，跨角色放行间留白，异常返回走底部专用通道。密集标签允许转为图下交接说明，不遮挡动作。体验行按 `user-journey` 的状态标签与结构化字段渲染，不在每格重复独立动作编号；阶段表头副文案为「业务阶段 / 关键结果」。

旅程数据显式区分 `type: current` 与 `type: target`；目标旅程的体验维度为「目标体验、支持设计、验证指标」，不沿用现状断点、用户需求、设计点子和衡量与证据四行。前提与异常恢复归入角色动作、返回连线和交接说明。目标动作填写 `experience`、`design`、`metrics` 三个字段。
